# DEVELOPMENT_RULES.md — 개발 규칙

> **목적**: 1인 개발 + AI 협업 환경에서 모든 코드 작업에 공통 적용되는 프로세스 규칙.
> 모든 작업의 공통 전제이므로 AI는 이 문서를 기본으로 숙지한다.

---

## 1. 작업 단위

- 하나의 작업 = 하나의 명확한 목적. "로그인 버그 수정 + 김에 리팩토링"처럼 목적을 섞지 않는다.
- 큰 기능은 독립적으로 검증 가능한 작은 단위로 쪼개서 순서대로 진행한다.
- 각 단위는 완료 시점에 빌드·테스트가 통과하는 상태여야 한다 (중간 상태로 방치 금지).

## 2. 브랜치 전략 (1인 개발 기준)

- 기본: `main` 브랜치는 항상 배포 가능한 상태를 유지한다.
- 규모가 있는 기능/실험은 `feat/<이름>`, 버그 수정은 `fix/<이름>` 브랜치에서 작업 후 main에 병합한다.
- 사소한 수정(오타, 문서, 한 줄 수정)은 main 직접 커밋 허용.
- **AI는 브랜치 삭제·force push·히스토리 재작성을 임의로 하지 않는다** (승인 필요).

## 3. 커밋 규칙

- 형식: `<타입>: <요약>` — 타입은 `feat` `fix` `refactor` `test` `docs` `chore` 사용.
- 요약은 한국어 또는 영어로 일관되게. 한국어
- 하나의 커밋에는 하나의 논리적 변경만 담는다. 관련 없는 파일을 함께 커밋하지 않는다.
- **AI는 사용자가 커밋을 요청했을 때만 커밋한다.** 임의로 커밋/푸시하지 않는다.
- 커밋 전 확인: 빌드 통과, 테스트 통과, 시크릿 미포함, 디버그 코드(console.log 등) 제거.

## 4. 작업 범위 (스코프) 규칙

1. 지시받은 작업 범위의 파일만 수정한다.
2. 범위 밖에서 버그·개선점을 발견하면: 수정하지 말고 `KNOWN_ISSUES.md`에 기록 + 작업 완료 보고 시 한 줄 언급.
3. 지시 작업 수행에 **필수적인** 범위 밖 수정(예: 시그니처 변경으로 호출부 수정 필요)은 허용하되, 보고에 명시한다.
4. 포매터가 자동으로 바꾸는 무관한 diff는 만들지 않는다 (수정한 부분만 포맷).

## 5. 완료 기준 (Definition of Done)

작업은 아래를 모두 만족해야 "완료"다:

- [ ] 요구된 기능이 동작한다 (직접 실행/테스트로 확인)
- [ ] 기존 테스트 전체 통과
- [ ] 신규 로직에 대한 테스트 존재 (`TESTING_GUIDELINES.md` 기준)
- [ ] 린트/포맷 통과
- [ ] 영향받는 문서 갱신 (`DOCUMENTATION_POLICY.md` 기준)
- [ ] 중요 결정이 있었다면 `DECISION_LOG.md` 기록

검증을 실행할 수 없는 환경이면 "미검증"임을 완료 보고에 반드시 명시한다.

## 6. 금지 사항 (승인 없이 하면 안 되는 것)

- 파일·디렉터리·브랜치·데이터 삭제
- 운영 환경 배포, 운영 DB 스키마 변경·마이그레이션 실행
- 외부로 데이터를 전송하는 신규 연동
- `.env` 등 시크릿 파일 수정
- 의존성 메이저 버전 업그레이드 (`DEPENDENCY_POLICY.md`)
- 히스토리 변경 (force push, rebase, reset --hard)

## 7. 보고 규칙

- 결과 중심으로 간결하게: 무엇을 바꿨는지, 검증 결과, 남은 것/가정 순.
- 과정 나열·자화자찬·불필요한 요약 반복은 하지 않는다.
- 문제가 생겼으면 시도한 것, 실패 원인, 선택지를 짧게 제시하고 판단은 소유자에게 넘긴다.
